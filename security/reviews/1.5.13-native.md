# KMP 1.5.13 native security reachability review

Reviewed October 22, 2026. **No risk acceptance is granted by this review.**
The released image still has vulnerable native libraries. The successful gate
means that no *fixable* High/Critical finding was present, not that all native
risk was accepted or eliminated.

## Runtime and application comparison

The production [Dockerfile](../../docker/Dockerfile.prod) selects official PHP
8.5.12 Apache/Trixie and installs the shared [runtime recipe](../../docker/install-runtime.sh).
Its final stage is separate from the Node and Composer builders; it copies
production Composer dependencies and application/utility-plugin source, not the
development vendor directory or Node runtime. Apache uses prefork and PHP;
DocumentRoot is `webroot`. Package presence and the original image configuration
come from the exact image's artifact, not the old September scan.

The image config has no non-root `User`. The entrypoint performs privileged
setup; Apache ordinarily drops request workers to `www-data`, while managed
CLI worker/admin commands have no explicit privilege drop in this production
recipe. Do not describe the whole runtime as rootless. The Azure templates do
not establish a no-new-privileges/all-capabilities-dropped contract. Restrictions
used for the local checks below are **test isolation only**. No running cloud
revision, environment override, host kernel or effective capability set was
inspected during this review.

[Managed Azure configuration](../../deploy/azure/main.bicep) serves port 80 behind
HTTPS ingress (`allowInsecure: false`). It sets `KMP_SKIP_CRON` and
`KMP_SKIP_MIGRATIONS` for managed roles; scheduler, backup and migration work run
through dedicated CLI jobs. Cron/systemd packages in the image do not establish
that their optional daemons are active. TLS termination does not mitigate a
native parsing memory error inside PHP.

The 200-package release inventory has no MariaDB server, server-core, backup,
CONNECT engine or Galera package; no systemd-homed; no Python/Python libxml2;
and no ImageMagick/Ghostscript. There are no corresponding binary copies in the
runtime recipe. These support component-absence assessments; direct filesystem
and process confirmation on the released AMD64 image remains outstanding.
External database servers and provider kernels require their own inventories.

Application paths reviewed:

- [HTTP middleware](../../app/src/Application.php) constructs Cake BodyParser
  with defaults. The shipped CakePHP class defaults `xml` to false; JSON and
  form requests do not automatically enter its XML parser.
- [Bootstrap Matching](../../app/plugins/Bootstrap/src/Utility/Matching.php)
  uses XMLReader, including `readInnerXML`, on generated navigation fragments
  from [HtmlHelper](../../app/plugins/Bootstrap/src/View/Helper/HtmlHelper.php).
  There is no explicit DTD rejection in that helper. Escaped labels/generated
  markup reduce control; they are not proof that libxml2 is unreachable.
- [Grid summaries](../../app/src/Services/GridSubscriptionReportService.php)
  parse server-rendered HTML with `DOMDocument::loadHTML(..., LIBXML_NONET)` and
  fixed DOMXPath expressions. Identity eligibility, grid allowlists and query
  scopes constrain input. A 50-row limit and text truncation after parsing do
  not bound every native allocation before parsing.
- Production Composer code exposes Cake `Xml::build()` and HTTP response
  `getXml()`. No application call to those raw XML consumers, XInclude,
  XPointer, custom XML resource loaders or DTD validation was found. This is a
  source-search result, not a proof about all future/transitive paths.
- [PDF processing](../../app/src/Services/PdfProcessingService.php) launches a
  bounded [PHP worker](../../app/bin/pdf-worker.php) with pure-PHP parsers;
  thumbnails use GD. It does not connect to X11 or spawn Ghostscript/ImageMagick.
- [Tenant backups](../../app/src/Services/BackupService.php) encode JSON with
  PHP gzip; [platform dumps](../../app/src/Services/Backups/PgDumpPlatformDatabaseBackupDumper.php)
  use `pg_dump`, and restores use `pg_restore`. No application
  `mariadb-dump`/`mysqldump`, Perl Archive::Tar, infocmp or mount invocation found.
- [GitHub issue submission](../../app/plugins/GitHubIssueSubmitter/src/Controller/IssuesController.php)
  creates an explicit HTTPS curl handle with headers/timeouts. No Negotiate
  service-name authentication or schemeless SFTP/SCP CLI path was found.
  The Docker health check uses explicit `http://localhost/livez`.

The highest relevant residual is libxml2. Debian's
[really2.9.14 status](https://security-tracker.debian.org/tracker/CVE-2026-6653)
explicitly retains the UAF. `LIBXML_NONET`, default external-entity restrictions,
HTTPS ingress and an empty fixable-findings list do not fix that memory defect.
The oversized-input bugs have additional prerequisites; resource limits reduce
opportunity but must not be credited as complete native memory-safety controls.
No exploitable KMP request was demonstrated, and no adversarial payload was sent
to production. This assessment does not establish that every transitive call is
unreachable.

For CVE-2026-86139, upstream documents a code-introduction/version qualification
that does not cleanly match Debian's reverted Trixie version string. For
CVE-2026-78409, upstream says the affected fast path starts in 2.42 while the image
has 2.41.5. The JSON preserves both vendor status and these qualifications;
neither is silently suppressed. Upstream util-linux advisory patch-version
metadata also differs from Debian's cited nsenter commit release: require the
actual vendor patch before claiming repair.

No runtime library is removed or replaced in this change. Replacing libxml2 with
