# Security infrastructure rollout

This change prepares infrastructure and application controls. Production remains unchanged until the existing POC and production release gates complete. Keep raw discovery output, what-if output, image scanner reports, and credential evidence in restricted operator storage.

## Database identities and ordering

Ordinary web and queue processes use distinct DML-only PostgreSQL roles through `DATABASE_URL` and `PLATFORM_DATABASE_URL`. Registered tenants retain their distinct runtime role/password. Runtime roles receive only CONNECT, schema USAGE, table SELECT/INSERT/UPDATE/DELETE, sequence USAGE/SELECT, and execution of application functions. They do not own databases, schemas, or tables and cannot create roles, databases, schemas, temporary tables, or persistent tables.

Only dedicated migration, provisioning, restore, and administrative-runner jobs receive `KMP_ADMIN_JOB=true`, `DATABASE_ADMIN_URL`, and `PLATFORM_DATABASE_ADMIN_URL`. Application bootstrap rejects administrative URLs in ordinary processes. The administrative connection is selected after local configuration, and tenant administrative work refuses a different database server. Configure one administrative job per database server when expanding beyond the current server.

Backup and restore subprocesses preserve the selected administrative port and TLS policy and ignore inherited libpq environment overrides. Generated database URLs use CakePHP-recognized `ssl=true&ssl_mode=require` options.

The normal scheduler/queue runner leaves operational platform jobs queued. The separate `${namePrefix}-admin` job runs `bin/cake platform jobs run --limit 1`. Give GitHub environments the new `AZURE_ADMIN_JOB_NAME` variable. All jobs receive the same verified image digest. Cutover validates process/identity separation, parks the admin schedule and waits for existing administrative executions before migrations, and resumes it after web health checks.

Use a maintenance window for the initial privilege transition:

1. Generate separate random runtime passwords, at least 24 bytes each, for `POSTGRES_RUNTIME_PASSWORD` and `PLATFORM_POSTGRES_RUNTIME_PASSWORD`. Supply these through the secure Bicep inputs. Runtime role names must be distinct from each other and from every tenant role and schema owner.
2. Review the Bicep what-if and first deploy with `enableApplicationRuntime=false`. Fresh bootstrap supports `--infra-only` for this stage; discover/review exact administrative-job and operator firewall rules with the explicit firewall `--pre-runtime` mode before resuming. The normal drift check always requires web discovery. Then complete role/migration preparation and apply `enableApplicationRuntime=true`; never point a new web revision at DML roles that have not been created. It creates a new runtime vault and new runtime/admin managed identities. The old vault retains administrative secrets and historical versions; the new runtime identity has no access to that vault. Dedicated admin jobs can read both vaults. Keep schedules parked and old web replicas stopped while switching identity/credentials and database ownership.
3. Run the migration job from the reviewed image. Its first `bin/cake platform database privileges` creates missing default/platform runtime roles and reconciles existing tenant roles. It transfers owned objects to the configured administrative owner, removes inherited roles and PUBLIC grants, and restricts default privileges. It is idempotent; it fails if a registered server differs, a runtime role is shared, an identifier is unsafe, or an administrative role is supplied as runtime. Review existing tenant role/secret bindings first: registrations that currently use the schema-owner role must be assigned a distinct runtime role and matching tenant secret through the administrative transition before reconciliation can proceed. Never rotate the administrative password through a tenant provisioning request. PostgreSQL provisioning requires explicit valid runtime URLs, reserves the platform runtime role, and permits reuse of the default runtime role only for its unchanged, already-registered tenant/database/server binding. Missing or conflicting bindings stop before password, secret, metadata, or SQL writes.
4. Run application/platform migrations, the missing-only environment secret import, backup-key reconciliation, and tenant migrations including suspended tenants. Re-run `platform database privileges` after migrations to verify/reconcile the complete registry. Backups and migration markers remain mandatory for pending tenant changes.
5. Exercise normal requests, queues, recovery, provisioning, restore into a disposable tenant, and an actual runtime-role cross-tenant connection denial in POC. Verify that ordinary managed identities cannot read either administrative URL or any historical administrative password version. Test schema-owner privileges on Azure itself: disposable local PostgreSQL cannot establish Azure server-admin role behavior.
6. While old web replicas remain stopped, remove the old managed identity from all apps/jobs, revoke its vault/storage assignments, and rotate the PostgreSQL administrative password. Update only the dedicated administrative vault/job URLs, and verify an administrative job with the new password. This rotation must precede runtime startup: historical backups or former tenant-secret values can contain the old owner password. Start the new web/runtime jobs, then the administrative runner, only after effective-access checks and this rotation pass. Retire remaining obsolete credentials after those checks.

The application never retrieves schema-owner credentials from its database-backed tenant secret store. The runtime vault contains only runtime configuration. Do not copy old administrative URL/password values into the new runtime vault.

Grant reconciliation transfers ownership and removes privilege; an old image that assumes runtime schema ownership is not a safe rollback. Roll back application behavior only with a compatible image, preserve the new role boundary, and use the dedicated administrative job for recovery. Never restore the broad database owner grants to make an old deployment pass.

## Document containers and encrypted archives

The new runtime identity receives a custom blob read/write/delete role on the explicitly inventoried document containers. It cannot create/delete containers, obtain delegation keys, or list blobs. The grant condition also denies `backups/*`, protecting historical archives in a shared document container. The dedicated archive container grants runtime only blob read permission for authorized encrypted-archive downloads; only administrative jobs can write/delete archives. Scheduled pruning enqueues an idempotent administrative job instead of deleting objects with the ordinary queue identity.

The administrative identity can create private document containers and manage blobs in the document account. Its role-assignment delegation is constrained to the fixed runtime principal and fixed blob-only document role. `TenantDocumentProvisioner` validates account/resource IDs and the reserved archive container before any external write, uses a management-audience identity token, and creates deterministic role assignments matching Bicep. Failed provisioning stops tenant activation. New role grants may take time to propagate; verify document access before announcing that a new tenant is ready.

`DOCUMENT_CONTAINERS_JSON` is a required, reviewed JSON array of existing document container names in environment parameter files and bootstrap. Validate it with `python3 deploy/azure/check-storage-inventory.py`. Run `bin/cake platform storage documents --dry-run` inside the dedicated administrative job to obtain the default plus registered tenant inventory, including suspended tenants. Compare it with the reviewed deployment inventory. The ordered migration job then runs `platform storage documents` before runtime cutover to ensure registered containers and their restricted grants. Keep the inventory updated when new tenants are provisioned.

Backups now read `Backups.storage` independently of `Documents.storage`. Azure requires `BACKUP_STORAGE_ADAPTER=azure`, explicit managed-identity settings, and `AZURE_BACKUP_STORAGE_CONTAINER` (the template defaults its dedicated container to `kmp-backups`). No document-container or credential fallback is allowed. S3 installations must explicitly configure `Backups.storage.s3` or `AWS_BACKUP_S3_BUCKET`; local installations keep `Backups.local.path`.

Before running the first migration or switching an existing installation to the archive container:

1. Inventory every existing `configured://`/legacy backup object and its source container in restricted operator evidence. During a paused-backup maintenance window, copy each object byte-for-byte into the dedicated archive container, preserving its `backups/` path and recorded object name. Detect conflicting names across source containers and stop rather than overwrite. Historical `local://` archives still use their explicit legacy local adapter and need a separate migration plan.
2. Compare object counts, byte lengths, and cryptographic hashes against backup metadata; restore an encrypted tenant and platform backup from the new container in disposable infrastructure. Preserve the original encrypted archive and recovery-key pairing. Do not delete source archives during this PR rollout.
3. Confirm the effective backend from inside both runtime and administrative identities: approved document write/read/delete succeeds, unassigned-container access fails, container creation and delegation-key requests fail for runtime, archive reads succeed, and archive writes/deletes fail for runtime while administrative backup/restore/retention succeeds. Test the historical `backups/*` denial and a newly provisioned tenant. Use synthetic canaries, wait for RBAC propagation, and record sanitized results. Compiled templates and mocked HTTP tests do not prove effective Azure RBAC.
4. Inspect all inherited subscription/resource-group/account assignments, detach the old shared identity, and remove its broad storage/vault roles through the release process. Verify managed identity is the backend actually used before retiring account credentials. The template disables shared-key access; credential retirement and production rollout remain incomplete until these probes pass.

Azure conditions are based on the [Storage ABAC contract](https://learn.microsoft.com/en-us/azure/storage/blobs/storage-auth-abac-examples?tabs=portal-visual-editor) and [constrained role-assignment delegation](https://learn.microsoft.com/en-us/azure/role-based-access-control/delegate-role-assignments-overview). The application shares one runtime identity across registered document containers; per-member access remains enforced by application policies. Container scoping limits account-wide permissions and does not claim per-request Azure identity isolation.

## Network restriction and retention

`reconcile-postgres-firewall.py` discovers current web and job outbound addresses and combines them with explicitly supplied operator sources. Run its planning mode, review its diff, and only apply during the monitored rollout. Discovery failures, missing addresses, and invalid ranges fail closed. Include the new administrative job in discovery. Remove the broad Azure exception only after exact rules and connectivity probes succeed; continue checking drift because Container Apps outbound addresses can change.

PostgreSQL backup retention is 35 days in the template. Confirm the effective production setting after rollout. The Bicep template alone does not establish that retention has changed on an existing server.

Document/backup storage networking remains unchanged. Azure Storage same-region public-IP rules do not provide the intended isolation. Private network isolation and cleanup of historical plaintext backups/logs are separate outstanding operational work. Validate effective managed-identity authentication and container permissions before removing old storage credentials.

## Local verification

- `bash deploy/azure/test-postgres-privileges.sh` starts an internal disposable Docker network and PostgreSQL server with a non-superuser schema owner, applies reconciliation twice, verifies runtime DML and future migration defaults, and rejects DDL, ownership changes, and cross-tenant/platform connections. It does not use the shared application test database. Set `KMP_TEST_PHP_IMAGE` to an installed PHP image with the app extensions; the default is `kmp-app:dev`.
- `az bicep build --file deploy/azure/main.bicep --outfile /tmp/kmp-main.json` validates syntax without deploying.
- `bash deploy/azure/test-runtime-contract.sh`, `python3 deploy/azure/test-postgres-firewall.py`, and `python3 -m unittest discover -s security -p 'test_*.py'` verify deployment and scanner contracts.

PHPStan is configured at level 0 across core and enabled plugins with the repository's existing per-file baseline; unmatched old entries are ignored to allow incremental cleanup. Missing rules, a tool crash, and any unbaselined error fail verification. No error-count heuristic is accepted. Raising the analysis level is a separate quality improvement; this configuration is not a substitute for security review.

When running `app/bin/verify.sh` in a container without Git metadata, generate a newline-separated app-relative changed-PHP file list from the same host checkout and set `KMP_VERIFY_CHANGED_PHP_FILE` to its mounted path. Missing Git metadata without that explicit manifest is a verification failure.

The development Compose stack includes a separate `admin-worker` service for queued provisioning/restore work. Its credentials are development-only; local reset/fixture tooling still uses the development owner. Use the disposable PostgreSQL test for actual least-privilege assertions. Do not place administrative URLs in a shared app `.env` consumed by web containers.

PostgreSQL 16 separates role membership from the ability to SET ROLE; reconciliation temporarily enables only the needed membership option and restores it afterward. See the [PostgreSQL role membership contract](https://www.postgresql.org/docs/16/role-membership.html) and [ownership transfer behavior](https://www.postgresql.org/docs/16/sql-reassign-owned.html).
